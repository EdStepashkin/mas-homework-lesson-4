# Порівняння підходів до побудови RAG: Naive, Sentence-Window та Parent-Child Retrieval

## Вступ
Системи Retrieval-Augmented Generation (RAG) стали ключовим компонентом для покращення здатності великих мовних моделей (LLM) генерувати фактично точні та контекстуально релевантні відповіді, використовуючи зовнішні бази знань. Однак, базові (naive) реалізації RAG часто стикаються з проблемами, пов'язаними з ефективністю пошуку та якістю контексту, що подається LLM. Це призвело до розробки більш досконалих стратегій, таких як Sentence-Window Retrieval та Parent-Child Retrieval, які прагнуть оптимізувати баланс між точністю пошуку та повнотою контексту.

## 1. Naive RAG (Базовий підхід)

### Опис
У базовому підході RAG, документ розбивається на чанки фіксованого розміру (наприклад, 256, 512 або 1024 токени/символи). Ці чанки вбудовуються у векторний простір. При отриманні запиту користувача, система шукає найбільш релевантні чанки, використовуючи векторний пошук, і передає їх безпосередньо LLM як контекст для генерації відповіді.

### Переваги
*   **Простота реалізації**: Легко налаштувати та впровадити.
*   **Швидкість**: Прямий пошук та передача чанків.

### Недоліки
*   **Ділема розміру чанка**:
    *   **Маленькі чанки**: Можуть призвести до більш точного пошуку, оскільки вбудовування краще відображає семантику невеликого фрагмента. Однак, LLM може не отримати достатньо контексту для генерації повної та зв'язної відповіді.
    *   **Великі чанки**: Надають більше контексту для LLM, але можуть містити багато "зайвого" тексту, що розмиває семантичне представлення і погіршує точність пошуку. Релевантна інформація може бути "захована" серед нерелевантної.
*   **Втрата контексту**: Важлива інформація може бути розділена між сусідніми чанками, що ускладнює її повне розуміння LLM.

## 2. Sentence-Window Retrieval (Пошук за вікном речень)

### Опис
Цей підхід є різновидом "small-to-big retrieval". Він спрямований на покращення точності пошуку при збереженні достатнього контексту для LLM.
1.  **Індексація**: Документ розбивається на окремі речення. Кожне речення вбудовується та індексується.
2.  **Пошук**: При отриманні запиту, система шукає найбільш релевантні *окремі речення*.
3.  **Розширення контексту**: Після знаходження релевантного речення, система розширює його, додаючи кілька сусідніх речень (так зване "вікно" речень) з обох боків. Це розширене вікно речень потім передається LLM як контекст.

### Переваги
*   **Точний пошук**: Використання малих, сфокусованих одиниць (речень) для пошуку покращує точність релевантності.
*   **Багатий контекст**: Розширення вікна забезпечує LLM достатнім контекстом для генерації якісної відповіді, мінімізуючи при цьому "шум" у контексті.
*   **Зменшення галюцинацій**: Завдяки більш релевантному та сфокусованому контексту, LLM менш схильна до галюцинацій.

### Недоліки
*   **Складність реалізації**: Вимагає більш складної логіки для індексації та розширення контексту.
*   **Обчислювальні витрати**: Може бути трохи дорожчим з точки зору обчислень через додаткові кроки.

## 3. Parent-Child Retrieval (Батьківсько-дочірній пошук)

### Опис
Parent-Child Retrieval також є ієрархічним підходом "small-to-big retrieval", який вирішує дилему контексту та точності.
1.  **Індексація**: Документ розбивається на два типи чанків:
    *   **Дочірні чанки (Child Chunks)**: Маленькі, сфокусовані фрагменти інформації (наприклад, окремі речення або невеликі абзаци), які використовуються для пошуку. Вони вбудовуються та індексуються.
    *   **Батьківські чанки (Parent Chunks)**: Більші, всеосяжні розділи (наприклад, цілі абзаци, розділи або навіть весь документ), які містять відповідні дочірні чанки. Вони не індексуються безпосередньо для пошуку, але зберігаються як джерело контексту.
2.  **Пошук**: При отриманні запиту, система шукає найбільш релевантні *дочірні чанки*.
3.  **Надання контексту**: Після знаходження релевантних дочірніх чанків, система ідентифікує їхні відповідні *батьківські чанки* і передає ці більші батьківські чанки LLM як контекст.

### Переваги
*   **Точний пошук**: Маленькі дочірні чанки забезпечують високу точність пошуку.
*   **Глибокий контекст**: Батьківські чанки надають LLM широкий та повний контекст, зберігаючи ширший наратив або передісторію.
*   **Гнучкість**: Дозволяє налаштовувати розміри дочірніх та батьківських чанків відповідно до структури документа та потреб.

### Недоліки
*   **Складність реалізації**: Найбільш складний з трьох підходів, вимагає ретельного проектування структури чанків.
*   **Управління даними**: Потребує ефективного управління зв'язками між дочірніми та батьківськими чанками.

## Порівняння підходів

| Характеристика          | Naive RAG                                  | Sentence-Window Retrieval                      | Parent-Child Retrieval                               |
| :---------------------- | :----------------------------------------- | :--------------------------------------------- | :--------------------------------------------------- |
| **Одиниця для пошуку**  | Чанки фіксованого розміру                  | Окремі речення                                 | Маленькі "дочірні" чанки (речення, невеликі абзаци) |
| **Одиниця для контексту** | Ті ж чанки, що й для пошуку                | Розширене "вікно" речень навколо знайденого    | Більші "батьківські" чанки (абзаци, розділи, документ) |
| **Точність пошуку**     | Залежить від розміру чанка, може бути низькою | Висока (завдяки малим одиницям)                | Висока (завдяки малим дочірнім чанкам)               |
| **Повнота контексту**   | Залежить від розміру чанка, може бути недостатньою | Достатня (завдяки розширеному вікну)           | Дуже висока (завдяки великим батьківським чанкам)    |
| **Складність**          | Низька                                     | Середня                                        | Висока                                               |
| **Використання**        | Прості випадки, швидке прототипування     | Коли потрібен точний пошук та достатній контекст | Коли потрібен глибокий контекст та висока точність пошуку |

## Висновки
Вибір підходу до RAG залежить від конкретних вимог до системи та характеристик даних.

*   **Naive RAG** є хорошим стартовим пунктом для простих застосувань, де швидкість розробки є пріоритетом, а вимоги до точності та повноти контексту не є критичними.
*   **Sentence-Window Retrieval** пропонує збалансоване рішення, покращуючи точність пошуку за рахунок використання малих одиниць, одночасно надаючи достатній контекст LLM. Це ефективний вибір для багатьох сценаріїв, де потрібно уникнути "шуму" у контексті.
*   **Parent-Child Retrieval** є найбільш просунутим підходом, що забезпечує найкращий баланс між точністю пошуку та повнотою контексту. Він ідеально підходить для складних систем, де потрібен глибокий контекст та висока якість відповідей, наприклад, у системах підтримки клієнтів або генерації контенту.
